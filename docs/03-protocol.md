# 03 通信协议

本文是控制端（安卓 App、网页）、信令服务器、被控端三方之间的约定。任何一方改动消息格式前，先改本文。

当前为**协议版本 2**：用账号登录，一个账号可以有多台电脑（被控端）和多个控制端，服务器只在同一账号内转发消息。版本 1（单一口令 + 被控端令牌）已废弃，服务器不再接受。

实现依据是 `server/lib/`、`host/`、`web/app.js`、`android/`。本文与代码不一致时以代码为准并修正本文。

## 1. 账号接口（HTTP）

- 地址：`https://<域名>/api/...`，与网页同源。本机测试是 `http://127.0.0.1:8787/api/...`。
- 方法一律 `POST`，请求体是 JSON（不超过 16 KB），响应体也是 JSON，响应头带 `Cache-Control: no-store`。
- 成功返回 HTTP 200；失败返回 4xx/5xx，响应体为 `{"error": "<错误码>", "message": "<中文说明>"}`，限流类错误另带 `retryAfter`（秒）。客户端可以直接把 `message` 显示给用户。

### 1.1 发送验证码

`POST /api/auth/send-code`

```json
{ "email": "a@example.com", "purpose": "register" }
```

`purpose` 是 `register`（注册）或 `reset`（找回密码）。成功：`{"ok": true, "cooldown": 60}`，`cooldown` 秒内不能对同一邮箱再发。

- 验证码 6 位数字，10 分钟内有效，最多可以输错 5 次，之后作废，需要重新发送。
- 注册时邮箱已被注册，返回 `email-taken`。
- 找回密码时邮箱没注册，**也返回成功**，但不发信。这样别人没法借这个接口试出哪些邮箱注册过。

### 1.2 注册

`POST /api/auth/register`

```json
{
  "email": "a@example.com",
  "code": "123456",
  "password": "至少 8 位",
  "clientType": "viewer",
  "deviceId": "k3J9...",
  "deviceName": "Xiaomi 13"
}
```

注册成功即视为登录，返回 `{"token": "...", "email": "a@example.com"}`。`clientType`、`deviceId`、`deviceName` 含义见 1.3。

### 1.3 登录

`POST /api/auth/login`

```json
{ "email": "a@example.com", "password": "...", "clientType": "host", "deviceId": "k3J9...", "deviceName": "LQ-PC" }
```

返回 `{"token": "...", "email": "a@example.com"}`。

| 字段 | 说明 |
|---|---|
| `clientType` | `host`（电脑上的被控端）或 `viewer`（手机 App、网页）。令牌只能用于对应的角色 |
| `deviceId` | 客户端第一次运行时随机生成并一直保存的设备编号，1–64 个字符，只能是字母、数字、`-`、`_`。不是机密 |
| `deviceName` | 给人看的设备名，最多 64 个字符。被控端用电脑名，控制端用手机型号或"浏览器" |

- 同一账号、同一角色、同一 `deviceId` 只保留一个有效令牌，重新登录会让旧令牌失效。
- 被控端的 `deviceId` 就是这台电脑在账号里的编号（下文的 `hostId`），`deviceName` 就是控制端列表里显示的电脑名。
- 令牌有效期：控制端 30 天，被控端 180 天，每次用它连上信令服务器都会从当时起重新计算。

### 1.4 重置密码

`POST /api/auth/reset-password`

```json
{ "email": "a@example.com", "code": "123456", "password": "新密码" }
```

返回 `{"ok": true}`。这个账号所有已登录的设备（包括电脑上的被控端）全部下线，需要用新密码重新登录。

### 1.5 退出登录

`POST /api/auth/logout`，请求头 `Authorization: Bearer <令牌>`，请求体可以为空。返回 `{"ok": true}`；令牌已失效时也返回成功。用这个令牌连着的信令连接会被服务器断开。

### 1.6 规则与错误码

| 项 | 规则 |
|---|---|
| 邮箱 | 去掉首尾空白、转小写后保存，最长 254 个字符 |
| 密码 | 8–128 个字符 |
| 发验证码 | 同一邮箱 60 秒一次、每天 10 次；同一 IP 每小时 10 次 |
| 登录失败 | 同一 IP 15 分钟内错 10 次、或同一邮箱 15 分钟内错 10 次，锁定 15 分钟 |

| 错误码 | HTTP | 含义 |
|---|---|---|
| `bad-request` | 400 | 请求格式不对 |
| `bad-email` | 400 | 邮箱格式不对 |
| `weak-password` | 400 | 密码不满足长度要求 |
| `bad-code` | 400 | 验证码错误或已过期 |
| `email-taken` | 409 | 该邮箱已注册 |
| `bad-credentials` | 401 | 邮箱或密码不对 |
| `unauthorized` | 401 | 令牌无效（退出登录接口不会返回它） |
| `registration-closed` | 403 | 服务器关闭了注册 |
| `too-many` | 429 | 操作太频繁，带 `retryAfter` |
| `mail-unavailable` | 503 | 服务器没有配置发信 |
| `mail-failed` | 502 | 发信失败 |

### 1.7 安装包（升级用）

说明见 [08 发布与升级](08-release-and-update.md)。都要带登录令牌 `Authorization: Bearer <令牌>`，手机和电脑的令牌都行；没带或无效回 401 `bad-token`。

**安卓 App 的最新版本** `GET /api/update/android`

```json
{
  "package": "com.remoteclaude.android",
  "versionCode": 8,
  "versionName": "0.7.0",
  "notes": "这次改了什么",
  "size": 26837338,
  "sha256": "<64 位十六进制>",
  "releasedAt": "2026-11-19T03:00:00.000Z",
  "url": "/download/android/RemoteClaude-0.7.0.apk"
}
```

还没发布过时回 404 `no-release`。App 只认 `package` 和自己一样、`versionCode` 比自己大的；下载后核对 `sha256`。

**下载** `GET /download/<渠道>/<文件名>`：渠道是 `android` 或 `host`，文件名只能是字母、数字和 `._-`。电脑被控端的自动升级读 `/download/host/latest.yml`（electron-builder 的格式），再下载里面写的安装程序。

支持单段的 `Range` 请求头（`bytes=a-b`、`bytes=a-`、`bytes=-n`），回 206 和 `Content-Range: bytes a-b/总长`；起点超出文件回 416 和 `Content-Range: bytes */总长`；多段的或看不懂的照常回 200 整个文件。所有回应都带 `Accept-Ranges: bytes`。App 断线后用它从断点接着下（服务器 2026-11-19 起）。

## 2. 信令通道（WebSocket）

- 地址：`wss://<域名>/ws`（本机测试是 `ws://127.0.0.1:8787/ws`）。
- 帧类型：文本帧，内容是一个 JSON 对象，必有字符串字段 `type`。二进制帧和无法解析的帧被丢弃。
- 心跳：服务器每 30 秒发一次 WebSocket ping，下一轮仍未收到 pong 就断开。客户端只需按标准自动回 pong。
- 大小限制：控制端发出的单条消息不超过 64 KB，超出被丢弃。

### 2.1 鉴权

连接建立后 **10 秒内**必须发送 `auth`，否则服务器以关闭码 4001 断开。鉴权成功前的其它消息一律忽略。

```json
{ "type": "auth", "role": "viewer", "token": "<登录得到的令牌>", "proto": 2, "client": "android/0.2.0" }
```

`role` 是 `viewer` 或 `host`，必须与令牌的 `clientType` 一致。`proto` 不是 2 时服务器拒绝。

控制端成功时收到：

```json
{
  "type": "auth-ok",
  "role": "viewer",
  "id": "a1b2c3d4e5f6",
  "email": "a@example.com",
  "iceServers": [ { "urls": ["turn:rc.example.com:3478?transport=udp"], "username": "1794990000", "credential": "<base64>" } ],
  "hosts": [ { "id": "k3J9...", "name": "LQ-PC", "online": true } ]
}
```

被控端成功时收到：

```json
{ "type": "auth-ok", "role": "host", "hostId": "k3J9...", "email": "a@example.com", "iceServers": [], "viewers": ["a1b2c3d4e5f6"] }
```

失败时服务器先发下面的消息，再以关闭码 4003 断开：

```json
{ "type": "auth-fail", "reason": "bad-token" }
```

| `reason` | 含义 | 客户端处理 |
|---|---|---|
| `bad-token` | 令牌无效、过期、角色不符 | 清掉本地令牌，回到登录页 |
| `revoked` | 令牌被注销（退出登录、重置密码） | 同上 |
| `bad-proto` | 协议版本不对 | 提示升级客户端 |
| `locked` | 该 IP 失败太多被暂时锁定 | 提示稍后再试，不要立即重连 |

要点：

- `id` 是本次连接的控制端编号，每次连接都会变。
- `hosts` 是这个账号下所有登录过的电脑，含当前不在线的；电脑在被控端上退出登录后就从列表里消失。
- `iceServers` 直接作为 WebRTC 的 ICE 服务器配置。其中 TURN 凭据是临时的（默认 24 小时），每次 `auth-ok` 都会重新签发，建立新的连接时用最近一次收到的。
- 被控端收到的 `viewers` 里可能有一个 `"push"`：账号登记了推送令牌时服务器加上的虚拟控制端（2.10），被控端照常对待即可。

### 2.2 消息转发规则

服务器只在**同一账号**内转发，只转发白名单内的类型，其余丢弃。

| 方向 | 允许的 `type` | 服务器的处理 |
|---|---|---|
| 控制端 → 被控端 | `list`、`select`、`answer`、`ice`、`stop`、`list-sessions`、`open-session`、`new-session`、`close-window`、`host-update`、`approval-answer`、`host-cmd` | 必须带 `host: <hostId>`。转发给该账号下这台电脑，并加上 `from: <控制端 id>`。电脑不在线时回 `{"type":"error","code":"host-offline","host":"..."}` |
| 被控端 → 控制端 | `windows`、`offer`、`ice`、`selected`、`error`、`window-closed`、`sessions`、`session-opened`、`session-failed`、`close-window-result`、`host-update-state`、`approvals`、`approval-result`、`host-state`、`host-cmd-result` | 必须带 `to: <控制端 id>`，且该控制端属于同一账号。服务器去掉 `to`、加上 `host: <hostId>` 后转发。`approvals` 另外交给推送（2.10）；发给虚拟控制端 `push` 的消息不转发 |
| 控制端 → 服务器 | `push-register`、`push-unregister` | 不带 `host`，服务器自己处理，不转发（2.10） |

服务器自己发出的消息：

| 发给 | 消息 | 时机 |
|---|---|---|
| 控制端 | `{ "type": "hosts", "hosts": [ ... ] }`，格式同 `auth-ok` 里的 `hosts` | 本账号有电脑上线、下线、登录、退出登录 |
| 被控端 | `{ "type": "viewer-join", "id": "…" }` | 本账号有控制端连上；`id` 为 `push` 时是账号有了推送令牌（2.10） |
| 被控端 | `{ "type": "viewer-leave", "id": "…" }` | 本账号有控制端断开；`id` 为 `push` 时是账号的推送令牌没了 |
| 控制端 | `{ "type": "push-register-result", "ok": true }` | 回 `push-register`（2.10） |
| 被控端 | `{ "type": "replaced" }` 后以 4002 关闭 | 同一台电脑（同一 `hostId`）又连上了一次，旧连接被顶替 |
| 任意 | `{ "type": "auth-fail", "reason": "revoked" }` 后以 4003 关闭 | 令牌被注销 |

一个账号可以同时有多台电脑在线、多个控制端在线，每个控制端各自选电脑、选窗口。

### 2.3 控制端发出的消息

下面所有消息都要带 `host`，即要操作的那台电脑的 `hostId`。

**请求窗口列表**

```json
{ "type": "list", "host": "k3J9...", "thumbs": "later" }
```

`thumbs: "later"` 可以不带。带上表示缩略图可以后补：被控端 0.9.7 起会分两次回 `windows`（见 2.4），先回的那份不用等截图；旧版被控端不认这个字段，照旧一次回完。

**选择窗口**。首次选择会触发 WebRTC 协商；已连通时再选会直接切换画面。

```json
{ "type": "select", "host": "k3J9...", "hwnd": 40571112 }
```

**WebRTC 应答**

```json
{ "type": "answer", "host": "k3J9...", "sdp": { "type": "answer", "sdp": "v=0\r\n…" } }
```

**ICE 候选**

```json
{ "type": "ice", "host": "k3J9...", "candidate": { "candidate": "candidate:…", "sdpMid": "0", "sdpMLineIndex": 0 } }
```

**停止查看**。被控端收到后关闭这条连接并停止采集。换电脑前要对原来那台发一次。

```json
{ "type": "stop", "host": "k3J9..." }
```

### 2.4 被控端发给控制端的消息

被控端发出时带 `to`，控制端收到时 `to` 已被去掉、多了 `host`。控制端应当只处理当前所选电脑发来的消息。

**窗口列表**（应答 `list`）

```json
{
  "type": "windows",
  "host": "k3J9...",
  "list": [
    {
      "hwnd": 40571112,
      "title": "Claude窗口远程控制工具",
      "minimized": false,
      "width": 854,
      "height": 1380,
      "thumb": "data:image/jpeg;base64,…",
      "closable": true
    }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `hwnd` | 窗口句柄，整数。窗口关闭后失效（Claude 的会话窗口关掉后只是藏起来，以后可能拿同一个句柄开别的会话），Claude 重启后会变 |
| `title` | 窗口标题，即会话名 |
| `minimized` | 是否最小化。最小化的窗口没有缩略图，选中时被控端会自动还原 |
| `width`、`height` | 窗口可见区域的物理像素尺寸；窗口最小化时这两个值没有意义 |
| `thumb` | JPEG 缩略图的 data URL，长边不超过 360 像素；取不到时为 `null` |
| `closable` | 能不能用 `close-window`（2.8）关掉。Claude 主窗口为 `false`，其余为 `true`。被控端 0.9.1 起才有，没有这个字段说明被控端不认 `close-window` |

列表不会主动推送，控制端需要时发 `list` 拉取。

**列表的顺序**（被控端 0.9.8 起）。按窗口在电脑屏幕上的位置排，和平铺摆出来的样子一致。控制端照收到的顺序显示，不要自己再排：

1. 先按屏。屏的先后就是平铺往屏上放窗口的先后（平铺配置的 `monitor_order`，默认从最左边的屏依次往右）；窗口算在它中心点所在的屏，中心点不在任何屏上时算最近的屏。
2. 同一个屏里从左到右，再从上到下（比窗口的中心点）。
3. 位置完全一样的（所有屏都放满以后叠在同一格的窗口）按 `hwnd` 从小到大。
4. 最小化的窗口按它还原后会回到的位置排，所以最小化、还原都不改变它的先后。取不到位置的排在最后，也按 `hwnd`。

只看位置，不看窗口参不参与平铺：自动平铺暂停了、平铺没在运行、Claude 主窗口、被拖到别处的窗口，都是这一套。所以选中窗口、在窗口里操作、刷新列表都不会改变顺序；窗口在电脑上挪了位置（重排、关掉一个后别的往前补、手动拖动），下一次拉到的列表才跟着变。`close-window` 之后推的列表、后补缩略图的两份列表也是这个顺序。

0.9.7 及以前的被控端给的是系统的窗口前后顺序：最近操作过的在最前，在手机上点进哪个窗口，它就排到第一个。

**缩略图后补**（被控端 0.9.7 起）。窗口的标题、个数枚举一下就有；缩略图要给电脑上所有窗口各截一张，要花大半秒，几十 KB 的图还要经服务器转发。`list` 带了 `thumbs: "later"` 时，被控端分两次回：

| 顺序 | 多出的字段 | 内容 |
|---|---|---|
| 先 | `"thumbs": "pending"` | 完整的列表，但每一项的 `thumb` 都是 `null`。控制端据此更新标题、个数、结束"正在刷新"，缩略图先沿用手上同一个 `hwnd` 的旧图 |
| 后 | `"thumbs": "done"` | 完整的列表，带缩略图，整份替换 |

`list` 没带 `thumbs: "later"`（旧版控制端、网页控制端），以及 `close-window` 之后推的那份列表，都是一次回完的，没有 `thumbs` 字段。

**WebRTC 提议**（应答首次 `select`）

```json
{ "type": "offer", "host": "k3J9...", "sdp": { "type": "offer", "sdp": "v=0\r\n…" }, "hwnd": 40571112, "title": "…" }
```

**已切换**（应答已连通状态下的 `select`）

```json
{ "type": "selected", "host": "k3J9...", "hwnd": 34407504, "title": "…" }
```

**ICE 候选**：格式同 2.3。

**窗口已关闭**：正在查看的窗口被关掉了（在电脑上关的，或者别的控制端用 2.8 的 `close-window` 关的）。控制端应回到会话列表。

```json
{ "type": "window-closed", "host": "k3J9..." }
```

**错误**

```json
{ "type": "error", "host": "k3J9...", "code": "capture-failed" }
```

| `code` | 来源 | 含义 |
|---|---|---|
| `capture-failed` | 被控端 | `select` 的窗口不存在、不在白名单内或采集失败 |
| `host-offline` | 服务器 | 消息要发给的电脑不在线 |

### 2.5 浏览、打开、新建 Claude 会话

除了已经打开的窗口（2.3 的 `list`），控制端还能浏览电脑上 Claude 桌面端的全部会话，点一个就在电脑上把它开成单独窗口，或者在某个环境下新建一个会话。被控端怎么做到的见 [07 浏览和打开 Claude 会话](07-claude-sessions.md)。这几条消息都走信令通道，不需要先建画面连接。网页版控制端暂不支持。

**请求会话目录**

```json
{ "type": "list-sessions", "host": "k3J9..." }
```

被控端回：

```json
{
  "type": "sessions",
  "host": "k3J9...",
  "available": true,
  "groups": [
    {
      "key": "env:6b896612-…",
      "name": "RemoteClaude",
      "folder": "F:\\SVNProjects\\RemoteClaude",
      "env": "6b896612-…",
      "sessions": [ { "id": "local_a775f944-…", "title": "Claude窗口远程控制工具", "at": 1795051127204, "open": true } ]
    },
    { "key": "dir:e:\\svnprojects\\gitprojects", "name": "GitProjects", "folder": "E:\\SVNProjects\\GitProjects", "env": null, "sessions": [] }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `available` | 为 `false` 时电脑上没找到 Claude 桌面端的会话记录，`reason` 是 `no-claude`，`groups` 为空 |
| `groups` | 已经排好序：有会话的组按最近活动排在前，没有会话的环境排在后 |
| `groups[].env` | 环境编号。为 `null` 的组是按工作目录分出来的（会话不属于任何保存过的环境），**不能在这组里新建** |
| `groups[].folder` | 工作目录，"无文件夹"组为空串 |
| `sessions[].id` | 会话编号，形如 `local_<uuid>` |
| `sessions[].at` | 最后活动时间，毫秒时间戳（电脑的时钟） |
| `sessions[].open` | 是否已经开成了单独窗口 |

已归档的会话不列，最多列 400 个。

**打开会话**

```json
{ "type": "open-session", "host": "k3J9...", "session": "local_a775f944-…", "req": "s1" }
```

**在某个环境下新建会话**

```json
{ "type": "new-session", "host": "k3J9...", "env": "6b896612-…", "req": "s2" }
```

`req` 是控制端自己起的编号（最长 40 个字符），回执原样带回，用来认是哪一次请求。电脑同一时间只做一件；打开时最慢要等 Claude 启动，控制端建议最多等 60 秒。

成功时被控端回：

```json
{ "type": "session-opened", "host": "k3J9...", "req": "s1", "hwnd": 1641336, "title": "Iphone摄像头", "created": true, "envOk": true }
```

| 字段 | 说明 |
|---|---|
| `hwnd`、`title` | 会话窗口，控制端接着按 2.3 发 `select` 去看它 |
| `created` | 为 `false` 表示会话本来就开着，没有新开窗口 |
| `envOk` | 只对新建有意义：为 `false` 表示新窗口开了，但没能自动选上环境，用户要在画面里自己选 |

新建出来的是一个空的新会话窗口（标题"新会话"），用户在画面里输入第一句话后会话才真正建立。

失败时被控端回：

```json
{ "type": "session-failed", "host": "k3J9...", "req": "s1", "code": "locked" }
```

| `code` | 含义 |
|---|---|
| `busy` | 电脑正在打开另一个会话 |
| `locked` | 电脑锁屏了，界面自动化用不了 |
| `not-found` | 会话或环境不存在（可能刚被删掉、归档） |
| `no-title` | 会话没有标题，没法在 Claude 界面里认出它 |
| `no-main` | Claude 主窗口没有出来（Claude 没装、启动不了） |
| `ui-missing` | 在 Claude 界面里没找到要点的按钮或菜单，通常是 Claude 升级改了界面，或者界面语言不是简体中文和英文 |
| `no-window` | 菜单点了，但没等到新窗口出来 |
| `stuck` | Claude 给的会话窗口一直停在别的页面上或一直没显示出内容，关掉重开一次也一样，要重启 Claude（见 07 第 6 节） |
| `timeout`、`failed` | 其它失败 |

### 2.6 被控端升级

控制端可以看电脑被控端的版本和升级状态，让它检查更新或马上升级（说明见 [08](08-release-and-update.md) 第 3 节）。

```json
{ "type": "host-update", "host": "k3J9...", "op": "status" }
```

`op` 是 `status`（只问状态）、`check`（检查更新）或 `install`（马上升级：已下好就重启换新，没下好就下好后马上换）。被控端回：

```json
{ "type": "host-update-state", "host": "k3J9...", "version": "0.7.0", "status": "downloading", "newVersion": "0.7.1", "percent": 35 }
```

| `status` | 含义 |
|---|---|
| `dev` | 从源码运行的开发版，不自动升级 |
| `idle` | 还没检查过 |
| `checking` | 正在检查 |
| `latest` | 已是最新 |
| `downloading` | 正在下载 `newVersion`，`percent` 是进度 |
| `ready` | 已下好，没人看画面时自动重启换新 |
| `installing` | 正在重启换新，随后会断开、重新上线 |
| `error` | 检查或下载失败 |

问过状态的控制端，之后状态有变化时被控端会主动推 `host-update-state`，直到它断开。被控端 0.7.0 以前的版本不认 `host-update`，不会回话。

### 2.7 手机审批

电脑上的 Claude Code 要审批工具调用或向用户提问时，在手机上作答（说明见 [09](09-approvals.md)）。

**被控端推送等待中的审批**（控制端连上时、列表有变化时；推给账号下所有连着的控制端，不只是在看画面的）：

```json
{ "type": "approvals", "host": "k3J9...", "list": [
  { "id": "1f0c9a2b3c4d5e6f", "kind": "permission", "title": "会话标题", "cwd": "F:\\proj", "agent": "",
    "tool": "Bash", "description": "构建并清理旧产物",
    "params": [ { "key": "command", "value": "npm run build" } ], "complete": true, "createdAt": 1795064248366 },
  { "id": "2a7d...", "kind": "ask", "title": "会话标题", "cwd": "F:\\proj", "agent": "", "tool": "AskUserQuestion",
    "questions": [ { "question": "用哪种数据库？", "header": "数据库", "multiSelect": false,
                     "options": [ { "label": "SQLite", "description": "单文件" } ] } ], "createdAt": 1795064249000 }
] }
```

`list` 是这台电脑上全部等待中的审批，空列表表示都处理完了。`complete` 为 `false` 表示参数太长被截断过。`agent` 非空表示是子代理发起的。

**控制端作答**：

```json
{ "type": "approval-answer", "host": "k3J9...", "id": "1f0c9a2b3c4d5e6f", "req": "a1", "choice": "deny", "text": "先别删 dist" }
{ "type": "approval-answer", "host": "k3J9...", "id": "2a7d...", "req": "a2", "choice": "allow",
  "answers": { "用哪种数据库？": "PostgreSQL", "要做哪些功能？": ["登录", "导出"] } }
```

`choice` 是 `allow` 或 `deny`；拒绝时 `text` 是给 Claude 的说明（可空）。回答提问时 `choice` 为 `allow`，`answers` 以问题原文为键，单选给字符串，多选给字符串数组，每个问题都要答；`choice` 为 `deny` 表示不回答。

**被控端回执**：

```json
{ "type": "approval-result", "host": "k3J9...", "id": "1f0c9a2b3c4d5e6f", "req": "a1", "ok": false, "code": "gone" }
```

| `code` | 含义 |
|---|---|
| `gone` | 已经在电脑上或别的手机上答了，或者已经结束 |
| `bad` | 答案不完整或格式不对 |
| `failed` | 写答案失败 |

被控端 0.8.0 以前的版本不推 `approvals`，也不认 `approval-answer`。

### 2.8 关闭会话窗口

控制端把电脑上的一个会话窗口关掉（手机"已打开"页签卡片上的关闭按钮）。效果和在电脑上点窗口的 × 一样：只是关掉窗口，会话不删，正在跑的任务接着跑，可以用 2.5 的 `open-session` 再打开。被控端怎么关见 [07](07-claude-sessions.md) 第 4 节。不需要先建画面连接。

```json
{ "type": "close-window", "host": "k3J9...", "hwnd": 4524954, "title": "通知声音提醒功能", "req": "c1" }
```

| 字段 | 说明 |
|---|---|
| `hwnd` | `windows` 列表里的句柄 |
| `title` | 控制端列表里这个窗口的标题，可不带。带了就要和电脑上现在的标题一致才关：Claude 会把关掉的窗口藏起来、以后拿它开别的会话，句柄不变，控制端的列表旧了时不能关错 |
| `req` | 控制端自己起的编号（最长 40 个字符），回执原样带回 |

被控端回：

```json
{ "type": "close-window-result", "host": "k3J9...", "req": "c1", "hwnd": 4524954, "ok": true }
{ "type": "close-window-result", "host": "k3J9...", "req": "c2", "hwnd": 199202, "ok": false, "code": "changed" }
```

| `code` | 含义 |
|---|---|
| `gone` | 电脑上已经没有这个窗口了（控制端当作已经关掉） |
| `changed` | 这个句柄现在是另一个标题的窗口，没有关 |
| `not-closable` | Claude 主窗口不能关（Claude 设置里关了托盘图标时，关主窗口会退出整个 Claude） |
| `still-open` | 发了关闭，3 秒后窗口还在 |
| `failed` | 其它失败 |

成功、`gone`、`changed` 时，被控端紧接着给这个控制端发一次新的 `windows` 列表。正在看这个窗口的其它控制端收到 `window-closed`。

被控端 0.9.1 以前的版本不认 `close-window`，不会回话；它们的 `windows` 列表里也没有 `closable`，控制端据此提示升级，不用等超时。

### 2.9 电脑状态、不连画面的命令

重排窗口、把会话提到最前、暂停平铺、锁定和解锁电脑，这几件事和具体哪个窗口无关。4.6、4.7 里它们走数据通道，要先选一个窗口、把画面连上才发得出去，锁屏和平铺的状态也只有连着画面的控制端知道。这一节让它们也能走信令通道：控制端停在会话列表、没看任何窗口时照样能用。被控端 0.9.6 起支持；数据通道上原来的消息照旧，网页控制端和旧版安卓端不受影响。

**电脑状态**（被控端 → 控制端）：

```json
{ "type": "host-state", "host": "k3J9...",
  "lock": { "locked": false, "unlock": true },
  "tile": { "available": true, "paused": false },
  "key": "MIIBojANBgkqhkiG9w0BAQEFAAOCAY8A…" }
```

| 字段 | 说明 |
|---|---|
| `lock` | 同 4.6 的 `lock` 消息：`locked` 电脑是否锁屏，`unlock` 电脑上是否装了解锁服务，`untrusted` 解锁服务要重新安装（只在为 `true` 时带） |
| `tile` | 同 4.7 的 `tile-state`：`available` 平铺是否在运行，`paused` 是否暂停 |
| `key` | 解锁时加密密码用的公钥（见下），DER（SubjectPublicKeyInfo）的 Base64。被控端刚启动、密钥还没生成好时没有这个字段，生成好后会再推一次 |

推给账号下**所有连着的控制端**（不只是在看画面的）：控制端连上时、被控端自己重新连上服务器时各推一次，之后锁屏、平铺状态或公钥有变化时再推。控制端按 `host` 分别记；电脑下线、自己和服务器断开时，记下的状态作废。

`host-state` 总是比这个控制端的第一份 `windows` 先发出。所以电脑回了窗口列表、却没推过 `host-state`，就说明被控端是 0.9.6 以前的版本，不认下面的命令，控制端据此提示升级，不用等超时。

**命令**（控制端 → 被控端）：

```json
{ "type": "host-cmd", "host": "k3J9...", "op": "arrange" }
{ "type": "host-cmd", "host": "k3J9...", "op": "unlock", "req": "u1", "enc": "<密文的 Base64>" }
```

| `op` | 作用 |
|---|---|
| `arrange`、`raise`、`pause`、`resume` | 窗口平铺的四个操作，同 4.7 的 `tile` 消息 |
| `lock` | 锁定电脑，同 4.6 的 `lock-now`。控制端同样要先请用户确认 |
| `unlock` | 解锁电脑，`enc` 是加密过的密码（见下），必须带 `req` |

`req` 是控制端自己起的编号（最长 40 个字符）。带了 `req` 的命令有回执，不带的没有（暂停、恢复、锁定之后会收到新的 `host-state`，一般不用回执）：

```json
{ "type": "host-cmd-result", "host": "k3J9...", "req": "u1", "op": "unlock", "ok": true }
{ "type": "host-cmd-result", "host": "k3J9...", "req": "u2", "op": "unlock", "ok": false, "code": "still-locked" }
```

| `code` | 含义 |
|---|---|
| `unavailable` | 平铺没在运行 |
| `bad-key` | 解锁的密文解不开：被控端重启过、换了密钥，控制端手里是旧公钥（新的会随 `host-state` 推来，重试即可）；或者密文格式不对 |
| `replayed` | 这条密文已经用过一次 |
| `bad-op` | 不认识的 `op` |
| `not-locked`、`no-service`、`bad-service`、`rate-limited`、`still-locked`、`no-logon-screen`、`busy`、`failed` | 解锁的结果，含义同 4.6 的表 |

**解锁密码的加密**。数据通道是端到端加密的，密码走它时服务器看不到（4.6）。信令通道要经服务器转发，所以密码不能明文走：

- 被控端每次启动生成一对 RSA 密钥（3072 位），私钥只在主进程的内存里，不落盘；公钥放在 `host-state` 的 `key` 里。
- 控制端用公钥加密密码的 UTF-8 字节：**RSA-OAEP，哈希和 MGF1 都用 SHA-256**，标签为空。密文的 Base64 放进 `enc`。3072 位密钥最多装 318 字节，超出的控制端直接提示，让用户到画面页（数据通道）解锁。
- 被控端的页面进程不解密，把密文原样交给主进程，主进程解开后交给本机的解锁服务。密码照旧不保存、不写日志（密文也不写）。
- **一条密文只认一次**：被控端记着解开过的密文（按密文字节的 SHA-256），再收到同样的回 `replayed`。OAEP 每次加密的结果都不同，正常的控制端不会发出重复的密文；这样服务器上即使有人把密文录了下来，也不能重发它来解锁。密文长度必须正好等于密钥长度（384 字节）。被控端重启后密钥换新，旧密文全部作废。
- 公钥经服务器转发，服务器要是被换成恶意的，可以把公钥换成自己的。这和画面连接是同一个信任前提：WebRTC 的证书指纹也是经服务器交换的。防的是服务器（或它的日志、抓包）被动看到密码。
- 控制端发出解锁请求后最多等 30 秒回执。

控制端的建议做法：连着画面、数据通道能用时照旧走数据通道（旧版被控端只认这条路）；没连画面时，对推过 `host-state` 的电脑走 `host-cmd`。

### 2.10 厂商推送（鸿蒙手机的系统通知）

鸿蒙 App（HarmonyOS NEXT 原生版，包名 `com.remoteclaude.mobile`）在后台保持不了信令连接。服务器在有新审批时通过华为推送服务（Push Kit）发系统通知，App 没开着也能收到（说明见 [09](09-approvals.md) 第 10 节）。服务器没配置推送时，下面的消息只回 `push-not-configured`，其余行为不变。

**控制端登记推送令牌**。每次鉴权成功后（含重连）都发一次，令牌变了也发：

```json
{ "type": "push-register", "platform": "harmony", "token": "<pushService.getToken() 拿到的令牌>" }
```

服务器回：

```json
{ "type": "push-register-result", "ok": true }
{ "type": "push-register-result", "ok": false, "error": "push-not-configured" }
```

| `error` | 含义 |
|---|---|
| `push-not-configured` | 服务器没配置推送 |
| `bad-platform` | `platform` 不认识（现在只有 `harmony`） |
| `bad-token` | 令牌为空、超过 512 个字符，或含空白、非 ASCII 字符 |
| `rate-limited` | 同一账号一分钟内登记超过 30 次 |
| `failed` | 服务器存令牌失败 |

规则：

- 同一个推送令牌只属于一个账号，谁最后登记归谁（同一台手机换了账号登录）。一个账号最多留 10 个令牌，多出的删最久没登记的。
- 推送令牌挂在登记它的那个登录上：这个控制端的登录令牌作废（退出登录、重置密码、同一设备重新登录、30 天没用过期）时，推送令牌一起删，已经退出的手机不会再收到推送。重新登录后 App 要再登记一次（按上面"每次鉴权成功后都发"就行）。
- 服务器说推送令牌无效时（应用卸载、令牌格式错误等）也会删掉，App 下次连上时重新登记即可。

**控制端注销推送令牌**（退出登录前、关掉通知时）。只删本账号的，没有回复：

```json
{ "type": "push-unregister", "token": "<令牌>" }
```

**虚拟控制端 `push`**。被控端只把 `approvals` 发给连着的控制端，手机 App 关着时服务器就看不到新审批。所以账号有推送令牌时，服务器对这个账号在线的电脑说有一个编号为 `push` 的控制端连着：电脑上线时放进 `auth-ok` 的 `viewers`，之后有了令牌发 `viewer-join`、令牌都没了发 `viewer-leave`。电脑像对真的控制端一样把 `approvals`（还有 `host-state`）发给它，服务器收下、不转发。被控端不用改，旧版本也能用。真的控制端编号是 12 位十六进制，不会和它撞。

**什么时候推**。服务器收到电脑发来的 `approvals`（发给谁都算），找出这个账号、这台电脑没推送过的审批，每条给账号下所有鸿蒙推送令牌发一条通知。推送过的记在数据库里（留 8 天，每个账号最多 5000 条，多了删最旧的），所以电脑重连、重发列表、对每个控制端各发一份、服务器重启，都不会重推；没有推送令牌时看到的审批也记下，之后登记的手机不会收到一串旧通知。同一台电脑连着发来的同一份列表只处理一次；每个账号每分钟最多处理 60 份列表，超了的不处理。推送因网络、超时、对方服务器出错或流控没发出去的，服务器隔 30 秒、2 分钟、10 分钟各重推一次，重推前这条已经不在电脑最近的列表里、或者电脑下线了就不推了（电脑重连后发来的列表会重新推），3 次都没成就等电脑下次发列表。每个账号每小时最多推 60 条（可配置，重推也算）；推满以后新来的审批先不推，这个小时过去后电脑再发列表时补推（被控端只在审批有变化、或者有控制端连上时才发，所以可能要等一会儿）。推送失败只记日志，不影响信令。

**通知内容**。默认（服务器配置 `showDetail` 为 `false`）只说有一条审批，不带工具名、会话名（窗口标题里可能有项目名）、命令和问题原文，这些不经过华为服务器，也不显示在锁屏上：

| 审批 | 标题 | 正文 |
|---|---|---|
| `kind` 为 `permission`，`tool` 为 `ExitPlanMode` 或 `计划` | `Claude 要你审批计划` | `打开 App 查看` |
| `kind` 为 `permission`，其余工具 | `Claude 要你审批` | `打开 App 查看` |
| `kind` 为 `ask` | `Claude 有问题要问你` | `打开 App 查看` |

服务器配置 `showDetail: true` 时带上细节：

| 审批 | 标题 | 正文 |
|---|---|---|
| `kind` 为 `permission`，`tool` 为 `ExitPlanMode` 或 `计划` | `Claude 要你审批计划` | 会话名：说明 |
| `kind` 为 `permission`，其余工具 | `Claude 要你审批：<tool>` | 会话名：说明（没有说明时用第一个参数） |
| `kind` 为 `ask` | `Claude 有问题要问你` | 会话名：第一个问题 |

正文合并空白，截到 100 个字符。

发给华为的请求（`POST https://push-api.cloud.huawei.com/v3/<projectId>/messages:send`，头 `Authorization: Bearer <JWT>`、`push-type: 0`）：

```json
{
  "payload": { "notification": {
    "category": "MARKETING",
    "title": "Claude 要你审批",
    "body": "打开 App 查看",
    "clickAction": { "actionType": 0, "data": { "approvalId": "1f0c9a2b3c4d5e6f", "hostId": "k3J9...", "kind": "permission" } },
    "notifyId": 1234567890
  } },
  "target": { "token": ["<账号下的推送令牌，最多 10 个>"] },
  "pushOptions": { "testMessage": true, "ttl": 86400 }
}
```

- 点通知打开 App 首页（`actionType: 0`），`clickAction.data` 的字段出现在 Want 的 `parameters` 里：冷启动在 `onCreate(want)`，热启动在 `onNewWant(want)`（UIAbility 要是 singleton）。App 拿 `approvalId` 和 `hostId` 打开审批面板。`actionType: 0` 要求入口 Ability 的 skills 里有 `entity.system.home` 和 `ohos.want.action.home`，而且不能配 `uris`，否则收不到。
- `notifyId` 由审批编号算出（SHA-256 前 4 字节，取 0～2147483647），同一条审批再推会覆盖旧通知，不会叠两条。
- `category` 和 `testMessage` 取自配置，没申请到自分类权益前只能用 `MARKETING` 加测试消息（09 第 10 节）。

## 3. WebRTC

| 项 | 约定 |
|---|---|
| 发起方 | **被控端发 offer**，控制端回 answer |
| ICE | Trickle ICE，候选通过信令通道的 `ice` 消息互换。对端描述设置前收到的候选要先缓存 |
| 视频 | 一个视频收发器，被控端 `sendonly`。没有音频 |
| 分辨率 | 等于窗口可见区域的物理像素尺寸，**会随窗口大小变化和切换窗口而改变**，控制端要处理分辨率变化事件 |
| 编码 | 默认 VP9 优先（被控端 0.8.3 起；之前按 Chromium 的协商顺序，通常是 VP8）。被控端配置 `codec` 可改成 `VP8`、`H264`、`AV1` 优先，`auto` 表示不干预。选 VP9 的原因见 05 的 2.14 |
| 码率与帧率 | 上限由被控端配置 `maxBitrateKbps`（默认 10000，0.8.3 之前是 4000）和 `maxFps`（默认 30）决定 |
| 起步码率 | 被控端收到 answer 后，给其中的视频编码补上 `x-google-start-bitrate`（配置 `startBitrateKbps`，默认 2500）再交给 `setRemoteDescription`。Chromium 发送端的带宽估计从对方描述里读这个值，不设时从 300kbps 起步，满屏文字一滚动要二十多秒才爬上去（0.8.3 起，`host/sdp.js`） |
| 数据通道 | 标签 `input`，有序可靠，**由被控端创建**，控制端在"收到数据通道"回调里拿到它 |
| 数据通道内容 | 文本消息，每条是一个 JSON 对象 |
| 传文件的通道 | 标签 `file`，有序可靠，**由控制端在第一次发文件时创建**（被控端 0.9.0 起，见 4.8）。不由被控端创建，是因为网页控制端不看通道标签，被控端多建一条会被它当成输入通道 |

连接恢复：

- 控制端的信令连接断开重连后会得到新的 `id`，旧的 WebRTC 连接随之作废（被控端收到 `viewer-leave` 会关掉它）。重连成功后重新发 `select`。
- WebRTC 连接状态变成 `failed`，或 `disconnected` 持续 5 秒，控制端先发 `stop` 再重新发 `select`。被控端会新建连接并重新发 `offer`。

## 4. 输入事件（数据通道，控制端 → 被控端）

所有坐标都是**相对坐标**：`x`、`y` 取值 0 到 1，表示在视频画面内的位置，(0, 0) 是左上角，(1, 1) 是右下角。被控端按窗口当前的实际尺寸换算成屏幕像素，所以控制端不需要知道窗口在屏幕上的位置和缩放比例。建议保留 5 位小数。

### 4.1 事件一览

| 事件 | 格式 | 说明 |
|---|---|---|
| 移动指针 | `{ "t": "m", "x": 0.5, "y": 0.5 }` | 目标窗口不在前台时被忽略，不会抢前台 |
| 按下鼠标键 | `{ "t": "d", "x": 0.5, "y": 0.5, "b": 0 }` | `b`：0 左键，1 中键，2 右键。会把窗口切到前台 |
| 松开鼠标键 | `{ "t": "u", "x": 0.5, "y": 0.5, "b": 0 }` | 没有对应的按下时被忽略 |
| 滚轮 | `{ "t": "w", "x": 0.5, "y": 0.5, "dx": 0, "dy": -120 }` | 见 4.2 |
| 敲一下按键 | `{ "t": "k", "k": "Enter", "m": 0 }` | 见 4.3。按下和松开一次完成，不支持按住 |
| 输入文字 | `{ "t": "t", "s": "你好" }` | 见 4.4 |
| 粘贴图片 | `{ "t": "img", ... }`、二进制帧、`{ "t": "img-end", ... }` | 见 4.5 |
| 发送文件 | 走 `file` 通道：`{ "t": "file", ... }`、二进制帧、`{ "t": "file-end", ... }` | 见 4.8 |
| 锁定电脑 | `{ "t": "lock-now" }` | 见 4.6 |
| 解锁电脑 | `{ "t": "unlock", "id": "u1", "p": "..." }` | 见 4.6 |
| 窗口平铺 | `{ "t": "tile", "op": "arrange" }` | 见 4.7 |

反方向（被控端 → 控制端）在这条通道上发的有：锁屏状态（4.6）、平铺状态（4.7）、能不能收文件（4.8）、电脑上新复制的文字（4.9）、图片回执和错误（4.5、第 5 节）。

一次点击 = 依次发 `m`、`d`、`u`。拖动 = `d`，若干 `m`，`u`。

移动和滚轮事件要做合并限流，建议每 16 毫秒最多各发一条。

### 4.2 滚轮

- 单位是 Windows 的滚轮增量：**鼠标滚轮一格 = 120**。可以发小于 120 的值实现平滑滚动。
- `dy` 为正：向上滚（内容向下移动）。`dy` 为负：向下滚。
- `dx` 为正：向右滚。
- 单条事件的 `dx`、`dy` 各自被限制在 ±2400 以内。
- 触摸拖动换算建议：手指移动对应的远程像素数 ≈ 滚轮增量（约 1 像素对 1 个单位）。手指向下拖，`dy` 为正。

### 4.3 按键

`k` 是键名，沿用网页 `KeyboardEvent.key` 的命名。支持的值：

| 类别 | 键名 |
|---|---|
| 编辑 | `Enter`、`Backspace`、`Delete`、`Tab`、`Escape`、`Insert`、空格（一个空格字符 `" "`） |
| 导航 | `ArrowUp`、`ArrowDown`、`ArrowLeft`、`ArrowRight`、`Home`、`End`、`PageUp`、`PageDown` |
| 功能键 | `F1` 到 `F12` |
| 字母数字 | 单个字符 `a` 到 `z`（不分大小写）、`0` 到 `9` |
| 符号 | 单个字符 `;` `=` `,` `-` `.` `/` `` ` `` `[` `\` `]` `'` |

不在表里的键名被忽略。

`m` 是修饰键位掩码，可相加：**1 = Ctrl，2 = Shift，4 = Alt**。例如全选是 `{ "t": "k", "k": "a", "m": 1 }`，Shift+Tab 是 `{ "t": "k", "k": "Tab", "m": 2 }`，换行（Shift+回车）是 `{ "t": "k", "k": "Enter", "m": 2 }`。

字母数字和符号键只用于组合键。**输入字符本身请用文字事件**，不要用按键事件拼。

安卓端 0.9.7 的"字体大小"用的就是这里的组合键：Ctrl+=（`"k": "=", "m": 1`）、Ctrl+-、Ctrl+0，对应 Claude 桌面端的放大、缩小、还原（见 [04](04-android-client.md)"调电脑上的字体大小"）。协议没有变。

### 4.4 文字

- `s` 是要输入的字符串，最长 20000 个字符，超出被截断。
- 被控端的处理：
  - 单行且不超过 40 个字符：逐字注入，不经过电脑上的输入法，中文、表情都可以。
  - 含换行或更长：写入电脑剪贴板后粘贴。**会覆盖电脑剪贴板的内容**。
- 文字里的换行不会触发发送。要发送消息，文字事件之后再发一个 `Enter` 按键事件。被控端按顺序串行处理，不需要控制端加延时。
- 逐字注入有节奏控制（每字约 8 毫秒，窗口首次收到按键后等 150 毫秒），40 个字符大约需要半秒。

### 4.5 图片

把控制端的一张图片粘贴进目标窗口的输入框，效果和在电脑上按 Ctrl+V 粘贴截图一样，不会自动发送。分三步，都走 `input` 数据通道：

1. 文本帧：`{ "t": "img", "id": "k3f9a2", "mime": "image/jpeg", "size": 345678 }`
2. 若干**二进制帧**：图片文件本身的字节，按顺序切块，每块不超过 16 KB。
3. 文本帧：`{ "t": "img-end", "id": "k3f9a2" }`

规则：

- `id` 由控制端生成，1 到 32 个字母或数字，用来对应回执。
- `mime` 只能是 `image/png` 或 `image/jpeg`。`size` 是字节数，上限 10 MB（10485760 字节），超出的直接回 `image-too-large`。
- 同一控制端同一时间只传一张。收到新的 `img` 时，还没传完的上一张直接丢弃。不在传图过程中收到的二进制帧被忽略。
- **顺序**：从收到 `img` 到这张图粘贴完成，期间收到的其它输入事件被控端先存着，粘贴完再按原顺序执行。所以控制端可以边传图边打字、按发送，这些操作都在图片之后生效。
- 被控端收齐后核对字节数、解码图片，写入电脑剪贴板（**会覆盖剪贴板原来的内容**），把目标窗口切到前台，按 Ctrl+V。
- 回执（被控端发给控制端）：成功是 `{ "t": "img-ok", "id": "k3f9a2" }`；失败是 `{ "t": "err", "code": "image-bad", "id": "k3f9a2" }`，错误码见第 5 节。图片相关的错误每次都回报，不受 1.5 秒限制。
- 传输中途 30 秒没收到新数据，被控端放弃这张图，回 `image-timeout`。
- 不论粘贴成功、失败还是超时，存下的输入事件都接着执行；只有数据通道关闭时才丢弃。收到新的 `img` 时，上一张存下的事件也先执行。
- 控制端发送前应自己处理图片：长边缩到 2048 像素以内；照片重新编码成 JPEG（质量 85 左右），截图这类 PNG 保持 PNG。重新编码会去掉照片里的拍摄位置等元数据，也能把照片按拍摄方向转正。
- 旧版被控端不认识这些消息，会静默忽略，控制端收不到回执。建议发完 20 秒还没有回执时，提示电脑上的被控端需要更新。

### 4.6 锁定与解锁

电脑锁屏后，系统不让任何程序切换窗口、注入键鼠、读写剪贴板，所有输入都会失败（回 `locked`）。这一节让控制端看到锁屏状态、远程锁定和解锁。**被控端不会在控制端断开时自动锁定**，锁定只在控制端明确要求时发生。

这一节的消息走数据通道，要先连上某个窗口的画面。被控端 0.9.6 起，锁屏状态、锁定、解锁也能走信令通道，不用连画面，见 2.9。

**锁屏状态**（被控端 → 控制端）：

```json
{ "t": "lock", "locked": true, "unlock": true }
```

- 数据通道打开时发一次，之后锁屏状态、`unlock` 或 `untrusted` 变化时再发。
- `unlock` 表示电脑上装了解锁服务（见 [06](06-unlock-service.md)），可以从控制端解锁。没装时控制端只能提示用户回到电脑前解锁。
- `untrusted: true`（被控端 0.9.28 起，只在为 `true` 时带，这时 `unlock` 是 `false`）：电脑上有解锁服务在跑，但被控端核实不过它，多半是被控端自动升级了、解锁服务还是旧版（06 的"升级"）。控制端提示"电脑上的解锁服务要重新安装"，不要显示成"没装"。旧控制端不认这个字段，照旧显示成没装。

**锁定**（控制端 → 被控端）：`{ "t": "lock-now" }`。被控端调用系统的锁定，效果和在电脑上按 Win+L 一样。没有回执，锁上后会收到 `locked: true` 的状态。控制端应先请用户确认；电脑上没装解锁服务时，提醒用户锁上后只能回到电脑前解锁。

**解锁**（控制端 → 被控端）：

```json
{ "t": "unlock", "id": "u1", "p": "Windows 登录密码或 PIN" }
```

回执：`{ "t": "unlock-result", "id": "u1", "ok": true }`，或 `{ "t": "unlock-result", "id": "u1", "ok": false, "code": "still-locked" }`。

| `code` | 含义 | 建议的提示 |
|---|---|---|
| `not-locked` | 电脑没有锁屏，什么都没做 | 电脑没有锁屏 |
| `no-service` | 电脑上没装解锁服务，或服务没在运行 | 电脑上没装解锁服务 |
| `bad-service` | 电脑上有解锁服务，但被控端核实不过它（多半是旧版，要重新安装），没有发密码。被控端 0.9.28 起 | 电脑上的解锁服务要重新安装 |
| `rate-limited` | 15 分钟内已经失败 3 次，暂停尝试，免得触发 Windows 的账户锁定 | 失败次数太多，15 分钟后再试 |
| `still-locked` | 已经输入，但电脑还是锁着：多半是密码或 PIN 不对 | 没解开，请检查密码或 PIN |
| `no-logon-screen` | 没找到锁屏的登录界面，为安全起见没有输入 | 没找到电脑的登录界面，没有输入密码 |
| `busy` | 上一次解锁还没结束 | 正在解锁，请稍候 |
| `failed` | 其它错误 | 解锁失败 |

规则：

- `p` 是用户每次在控制端输入的密码，控制端和被控端都**不保存、不写日志**。它只在内存里经过：数据通道（DTLS 端到端加密，经中继服务器转发也看不到内容）→ 被控端 → 本机的解锁服务。
- 锁定、解锁消息不排在传图队列里，收到就处理。
- 控制端发出解锁请求后最多等 30 秒回执。

### 4.7 窗口平铺

被控端自带 Claude 会话窗口的自动平铺（原来的 claude-window-tiler 插件并进来了）：每屏固定放 3 个、关窗口补位、新开会话后把主窗口收到托盘、切到 Claude 时把所有会话窗口提到最前。控制端可以远程触发其中几项。

**平铺状态**（被控端 → 控制端）：`{ "t": "tile-state", "available": true, "paused": false }`。数据通道打开时发一次，暂停状态变化时再发。`available` 为 false 表示平铺没在运行，控制端应隐藏相关菜单。

**操作**（控制端 → 被控端）：`{ "t": "tile", "op": "arrange" }`，`op` 取值：

| `op` | 作用 |
|---|---|
| `arrange` | 立即重排一次（暂停时也能用） |
| `raise` | 把所有会话窗口提到最前 |
| `pause` | 暂停自动平铺：新开、关闭窗口时不再自动重排 |
| `resume` | 恢复自动平铺 |

没有回执；暂停、恢复后会收到新的 `tile-state`。这些消息不排在传图队列里。

被控端为远程输入把窗口切到前台时，不会触发"把所有会话窗口提到最前"，免得手机上点一下就把电脑上所有 Claude 窗口都翻出来。

被控端 0.9.6 起，平铺状态和这四个操作也能走信令通道，不用连画面，见 2.9。

### 4.8 发送文件

把控制端的任意文件存到电脑上，再把它在电脑上的完整路径粘贴进当前查看的窗口的输入框，Claude 就能按路径去读。不会自动发送。被控端 0.9.0 起支持，网页控制端暂不支持。

**为什么单开一条通道**：文件可能有几十 MB，在慢网络上要传好几分钟。和图片一样走 `input` 通道的话，点击、滚动、打字都要排在文件数据后面。`file` 通道和 `input` 通道是同一个连接里的两路，各自有序，互不排队（实测见 05 的 2.16）。信令通道单条只有 64 KB，还要经服务器转发，不适合传文件。

**能不能发**（被控端 → 控制端，`input` 通道）：数据通道打开时被控端发

```json
{ "t": "file-caps", "max": 52428800 }
```

`max` 是单个文件的字节数上限。没收到这条说明被控端版本太旧，控制端应提示更新被控端，不要发。旧版控制端不认这条消息，会忽略。

**发送**（控制端 → 被控端）。控制端第一次发文件时建标签为 `file` 的数据通道（有序可靠），等它打开后：

1. 文本帧：`{ "t": "file", "id": "f3k9a2", "name": "季度报告.pdf", "size": 3456789 }`
2. 若干**二进制帧**：文件本身的字节，按顺序切块，每块不超过 16 KB。
3. 文本帧：`{ "t": "file-end", "id": "f3k9a2", "sha256": "<整个文件的 SHA-256，64 位小写十六进制>" }`

取消：`{ "t": "file-cancel", "id": "f3k9a2" }`，走 `input` 通道，不用排在 `file` 通道里还没发完的数据后面（`file` 通道上发也认）。被控端删掉已经收到的部分，不回执。

规则：

- `id` 由控制端生成，1 到 32 个字母或数字。`name` 是文件原来的名字，`size` 是字节数，可以为 0。
- 同一控制端同一时间只传一个。收到新的 `file` 时，还没传完的上一个直接丢弃。不在传文件过程中收到的二进制帧、对不上 `id` 的 `file-end` 被忽略。
- 被控端边收边写进存放目录下的 `.partial\` 里的临时文件，收齐后核对字节数和 SHA-256（`sha256` 为空时只核对字节数），再改成正式文件名。临时文件在取消、出错、超时、连接断开时删掉；被控端启动时删掉放了一个小时以上的。
- **存放目录**：默认是电脑"下载"文件夹下的 `RemoteClaude`（如 `C:\Users\<用户>\Downloads\RemoteClaude`），被控端配置 `fileDir` 可改。放在"下载"里，电脑前的人好找，也不受 Claude 商店版把 `%APPDATA%` 转到别处的影响。
- **文件名**：只取最后一段（去掉路径），去掉控制字符，`<>:"|?*` 换成下划线，去掉结尾的点和空格，`CON`、`NUL`、`COM1` 这类保留名前面加下划线，超过 120 个字符时截短（保留扩展名）。**同名不覆盖**：已有 `报告.pdf` 时存成 `报告 (1).pdf`，再有就是 `(2)`，和 Windows 资源管理器一样，不分大小写。
- **粘贴**：存好后被控端把路径写进电脑剪贴板（**会覆盖剪贴板原来的内容**），把收完时正在查看的窗口切到前台，按 Ctrl+V。路径里有空白时加双引号；末尾加一个空格，接着打字不会和路径连在一起。和其它输入一样串行执行。
- 磁盘剩余空间不够"文件大小 + 64 MB"时，收到 `file` 就回 `disk-full`，控制端不用把整个文件传完。
- 传输中途 30 秒没收到新数据，被控端放弃，回 `file-timeout`。
- **和其它输入的先后**：文件和输入不在一条通道上，被控端不替控制端排队。控制端要保证"先路径后文字"的，应等收到回执再发文字（安卓端在发文件期间不让点"发送"，见 04）。

**回执**（被控端 → 控制端，`file` 通道）：

```json
{ "t": "file-ok", "id": "f3k9a2", "path": "C:\\Users\\a\\Downloads\\RemoteClaude\\季度报告 (1).pdf", "name": "季度报告 (1).pdf", "pasted": true }
{ "t": "file-ok", "id": "f3k9a2", "path": "C:\\…\\季度报告.pdf", "name": "季度报告.pdf", "pasted": false, "code": "locked" }
{ "t": "err", "code": "disk-full", "id": "f3k9a2" }
```

- `file-ok` 表示**文件已经存好**。`name` 是实际存的文件名（同名时带编号）。`pasted` 为 `false` 时路径没能粘贴进去，`code` 是原因（`locked`、`front-failed`、`window-gone`、`failed`），文件照样留在电脑上。
- `err` 表示没存下，错误码见第 5 节。

控制端的建议做法：

- 发送前对照 `file-caps` 的 `max` 检查大小，超出的直接提示，不要发。
- 一边发一边算 SHA-256，发完放进 `file-end`。
- 数据通道里排队超过 1 MB 就等一等；进度按"已交给通道的字节数 − 通道里还排着的字节数"算。排着的数据 30 秒一点都没发出去，算传输卡住了，取消并提示。
- 发完以后最多等 30 秒回执。
- `pasted` 为 `false` 时，把路径放到控制端自己的输入框里，用户等电脑能操作了（比如解锁后）再发出去。

### 4.9 剪贴板回传

方向和前面相反：**被控端 → 控制端**，走 `input` 通道。控制端在看某个窗口的画面期间，电脑上新复制了文字（包括在控制端上点了 Claude 界面里的"复制"按钮、选中后按 Ctrl+C），被控端把这段文字发过来，控制端放进自己的剪贴板。被控端 0.9.9 起、安卓端 0.9.6 起支持，网页控制端暂不支持。内容只走数据通道（DTLS 端到端加密），不经过服务器。

**消息**。一段文字切成若干块，按顺序发：

```json
{ "t": "clip", "id": "c7", "i": 0, "n": 3, "s": "第一块的文字…" }
{ "t": "clip", "id": "c7", "i": 1, "n": 3, "s": "第二块…" }
{ "t": "clip", "id": "c7", "i": 2, "n": 3, "s": "最后一块" }
```

- `id` 是这一段的编号，1 到 32 个字母或数字，同一段的各块相同。`n` 是总块数，`i` 是这一块的序号，从 0 起。短文字只有一块（`i` 为 0，`n` 为 1）。
- 每块的 `s` 不超过 4000 个字符（UTF-16 单元），全是中文时一条约 12 KB。被控端不会把一个代理对（表情这类字符）切在两块里。
- 换行统一成 `\n`（Windows 剪贴板里是 `\r\n`）。
- 一段最多 100000 个字符。超过的不发内容，只发 `{ "t": "clip-skip", "code": "too-large" }`，控制端提示"电脑上复制的文字太长"。`code` 以后可能有别的值，不认识的忽略。
- 控制端收到 `i` 为 0 的块就开始新的一段，还没拼完的上一段丢掉；中途来了对不上的块（`id` 换了、`n` 变了、`i` 不是下一个），整段丢掉。拼齐后写进本机剪贴板并提示一下。
- 没有回执。

**被控端什么时候发**：

- 只在**有控制端连着画面**时看剪贴板，没人看的时候不读。每 300 毫秒看一次系统的剪贴板序号（只读一个数，不打开剪贴板），变了才去读，读之前先等 120 毫秒让复制的程序写完。
- 只发**连上画面之后发生的变化**，连上之前就在剪贴板里的内容不发。用户定的：只自动同步，没有"取电脑剪贴板"的按钮；要取之前的内容，在电脑上（或隔着画面）再复制一次。
- 发给所有连着数据通道的控制端。
- **不发的情况**：剪贴板里没有文字（图片、文件）；电脑锁屏（系统不让读）；内容带着 `ExcludeClipboardContentFromMonitorProcessing` 或 `Clipboard Viewer Ignore` 格式（密码管理器用它们表示"监视剪贴板的程序不要处理"）；被控端自己为粘贴写进去的内容（4.4 的长文字、4.5 的图片、4.8 的文件路径），那是控制端刚发来的，不用再发回去。这些情况都没有消息，控制端什么也收不到。
- 同样的文字 1.5 秒内只发一次（有的程序一次复制会让剪贴板序号变好几回）。
- 被控端的日志只记字符数，不记内容。
- 被控端配置 `clipboardSync` 写成 `false` 可以整个关掉；安卓端设置里的"同步电脑剪贴板"关掉后，收到了也不写进手机剪贴板。

旧版控制端、网页控制端不认 `clip` 和 `clip-skip`，会忽略。旧版被控端不发，控制端什么都不用做。

## 5. 被控端通过数据通道回报的错误

```json
{ "t": "err", "code": "front-failed" }
{ "t": "err", "code": "front-failed", "detail": "最前面是管理员权限的「任务管理器」（taskmgr.exe），被控端切不走它，请在电脑上关掉或最小化它" }
```

`detail` 可以没有，有的话是被控端写好的一句补充说明，控制端接在按 `code` 翻好的提示后面，用"："隔开，比如"电脑上无法把该窗口切到前台：最前面是……"。控制端去掉里面的控制字符和首尾空白，最多显示 200 个字符，空的当作没有。被控端 0.9.30 起在 `front-failed` 上带：切不到前台时，说出挡在最前面的是哪个窗口（标题最多 30 个字符，加上程序名），以管理员权限运行的会注明。被控端是普通权限，Windows 不让它把管理员权限的窗口换下去，也不让它往里发键盘鼠标，这是"一直切不到前台"最常见的原因。电脑上没有前台窗口时说明是"电脑上现在没有窗口在前台"。旧版被控端不带，旧版控制端不认、照旧只显示提示。

| `code` | 含义 | 建议的提示 |
|---|---|---|
| `front-failed` | 无法把目标窗口切到前台，这次输入被丢弃 | 电脑上无法把该窗口切到前台 |
| `locked` | 电脑锁屏了。锁屏时系统不让程序切换窗口、注入键鼠、读写剪贴板，所有输入都会失败；画面通常还能看 | 电脑锁屏了，解锁后才能操作 |
| `covered` | 点击位置被电脑上别的窗口挡住，这次输入被丢弃 | 点击位置被其它窗口挡住了 |
| `window-gone` | 目标窗口已关闭 | 该窗口已关闭 |
| `image-too-large` | 图片超过 10 MB | 图片太大了 |
| `image-bad` | 图片字节数不对或无法解码 | 图片数据有误，没能粘贴 |
| `image-timeout` | 传图中途 30 秒没有新数据 | 图片传输中断了 |
| `file-too-large` | 文件超过 `file-caps` 的上限（50 MB） | 文件太大了 |
| `file-bad` | 文件消息格式不对，或者字节数、SHA-256 对不上 | 文件传输出错，电脑没有保存 |
| `file-timeout` | 传文件中途 30 秒没有新数据 | 文件传输中断了 |
| `disk-full` | 电脑磁盘剩余空间不够 | 电脑的磁盘空间不够了 |
| `file-failed` | 电脑上写文件失败 | 电脑上保存文件失败 |

同一控制端同一错误码每 1.5 秒最多回报一次（图片、文件相关的除外）。图片、文件的回执带 `id`，其它错误没有。文件的错误走 `file` 通道。

## 7. 协议后续演进

以下是建议，尚未实现，改动前请先更新本文：

- **设备管理**：列出账号下已登录的设备，远程让某台下线。
- **窗口列表推送**：窗口新增、关闭、改名时被控端主动发 `windows`。
- **剪贴板回传的后续**（文字已经做了，见 4.9）：剪贴板里的图片；控制端主动取电脑剪贴板里现有的内容；网页控制端。
- **文件断点续传**：连接断了（切网络、切后台太久）以后从断点接着发。现在要从头再发一次（4.8）。
- **指针位置回传**：把电脑上真实指针的位置和形状发给控制端。
