其它结果：

- **正式版**：开启代码裁剪编译通过，安装包 25.5 MB；调试版 36 MB。

### 2.3 未验证

接手后请优先补上这些：

- **真机**。安卓 App 只在模拟器上跑过：硬件解码、真实触摸手感、双指缩放、发热和耗电都没测。
- **对真实 Claude 窗口的输入**。为了不往用户正在用的会话里乱打字，输入只在测试窗口上验证过。在 Claude 窗口里点击、往输入框打字、发送消息、滚动对话，都还没有实测（T3）。
- **手机经公网连生产服务器**（T1 验收第 3 条、A17）。服务器各部分已分别验证（见 2.4），但还没有用手机在移动网络下完整走一遍。生产口令只能由用户本人输入，这一步需要用户在手机上做。
- **安卓端**：A3 精确计时、A8 缩放、A14 网络切换、A17 公网、指纹锁（模拟器没设锁屏，验证框没弹出过）、"窗口被挡住"提示。
- 电脑浏览器的直接键盘输入、鼠标拖动。
- 口令输错 5 次后的锁定。
- 多个控制端同时连接。
- 最小化窗口被选中时的自动还原。
- 被控端被顶替（`replaced`）的流程。
- 长时间运行的稳定性、CPU 和内存占用。
- 服务器整机重启后的自动恢复（Docker 已设开机自启、容器重启策略 `unless-stopped`，但没有真的重启过：这台服务器上还跑着别的生产网站）。

### 2.12 手机下载慢（2026-11-19，生产）

用户手机上 App 内升级到 0.8.0 时下载很慢。在服务器的 Caddy 容器里看这条连接：手机（内地电信网络）到香港服务器往返约 230ms，重传约 10%，拥塞控制是默认的 cubic，拥塞窗口只剩 2 到 4 个包，实际约 15 KB/s（27 MB 要半小时）。电脑那边走的是香港出口，不受影响。

- 服务器改用 BBR（用户同意），说明和改回去的办法见 [08](08-release-and-update.md) 第 5 节末尾；改完服务器上的几个网站都正常回 200。只对新连接生效，当时正在下的那条还是 cubic。
- 服务器下载接口加了 `Range`，App 加了断点续传（0.8.1 起）：单元测试里用会中途掐断连接的本机服务器测了断三次接着下、上次没下完的接着下、服务器不支持续传时从头下、校验不对删掉、一直下不动放弃、401 不重试。
- 改成 BBR 后用户在手机上重新下载，反馈"快多了"。
- **还没测**：生产服务器上带令牌的 206 回应（没有拿用户的令牌去试，Caddy 默认原样转发 Range）。

| 带宽估计 | 常掉到 100kbps 以下 | 3.3～5.4M | 从 1.7M 爬到 5.2M | 3.9～8M |
| 滑动时每秒发出的帧 | 0～1 | 多数 5～9 | 多数 3～5 | 中位数 28.7（四分位 28.6～29.7） |

- **网络**：电脑没有公网 IPv6，手机在电信 5G 上，两边直连不上，画面一直绕香港中继。电脑到香港 237ms、到腾讯云广州 19ms。用户买了一台腾讯云广州轻量服务器 `rc-gz`（2 核 1G，峰值 200Mbps），只装 coturn（系统包 4.6.1），配置照香港的改 IP，共享密钥直接用香港的（从香港管道传过去，没有落地显示）。香港信令服务器的 `iceServers` 和 `turn.urls` 把广州排在前面、香港留作备用（旧配置有备份），重启信令服务。从本机直接向两边申请中继：广州 10/10 回应、往返 26ms、用同一个密钥申请成功；香港 6/10 回应、往返 237ms。实际连接走的是电脑一侧的广州中继（`relay/udp` → 手机 `prflx`）。
- **码率上限**：4M 时滑动的帧被码率压住。提到 10M 后体感差不多：每次打开画面是新连接，带宽估计从 1.7M 起步，二十多秒才爬到 5M，根本没碰到上限。
- **编码**：满屏文字滚动时 VP8 一帧要 90KB 上下，3M 只够四五帧。换 VP9 后同样的网络滑动时每秒发 28～30 帧，发送 4～5M，编码每帧约 5ms（i7-14700KF 软编）。用户说"顺了一些"。被控端代码的默认值改成 VP9、上限 10M（下次发布被控端时生效）；用户电脑上现在靠 `%APPDATA%\remote-claude-host\config.json`（`{ "maxBitrateKbps": 10000, "codec": "VP9" }`）生效。
- 广州服务器绑登录公钥时出过岔子：用户照着截图手工转写公钥，被认错了好几个字符，绑上去的是一把错的钥匙。后来在 App 0.8.2 的提问卡片里把整条命令发到手机上一键复制才绑对，这也是 2.15"一键复制"的由来。
- **起步码率和 60 帧**（同日，用户说"接着优化"）：电脑那边滑动时每秒抓到 29～30 帧新画面，说明 Claude 界面并不是一格一格跳，所以没改滚轮。被控端收到 answer 后补上 `x-google-start-bitrate`（`host/sdp.js`，默认 2500kbps）：先在浏览器里用两个本页连接对比，不加时连接建立后带宽估计是 300kbps，加了是 2500kbps。再用开发版被控端接正式服务器、帧率上限 60 试了一次，用户说"稍微有点改进"，但不需要这么好的效果，担心流量，要求帧率回到 30。滑动时流量大致和帧数成正比；VP9、30 帧一直来回滑约 15MB/分钟，静止不到 1MB/分钟。
- 发布被控端 0.8.3（起步码率、默认 VP9 和 10Mbps，帧率 30），用安装程序静默装到用户电脑上，服务器日志里是 `host/0.8.3`。用户电脑的 `%APPDATA%\remote-claude-host\config.json` 还留着 `{ "maxBitrateKbps": 10000, "codec": "VP9" }`，和新默认值一样，没删。
- **还没测**：手机这边实际显示多少帧（App 的统计浮层，用户没报数）；装上 0.8.3 后刚打开就滑的体感；手机发热；用户在 Wi-Fi 下的情况。

### 2.23 打开会话"卡住"的真正原因：显示器关着（被控端 0.9.5，2026-11-20，用户电脑）

- 读 Claude 的界面代码（`ion-dist.asar` 里的 `[electron-window] Pool`）：关掉的会话窗口清空后藏进窗口池，至少留 1 个，下次开窗口先用它；拿出来时马上把新标题写进页面。所以页面标题还是旧的，说明是窗口没刷新画面，不是会话加载慢。
- 系统日志 Kernel-Power 566（自动息屏、有输入亮屏的记录）：这台电脑 5 分钟没人操作关显示器。昨天和今天两次事故一共 13 次失败，全部落在息屏时段里；显示器亮着时复用同一批窗口都是秒开。
- 被控端只在有人看画面时防息屏，手机停在会话列表时不防，防息屏也叫不醒已经关掉的显示器；打开、新建会话全程用界面自动化，不发鼠标键盘，显示器一直不亮。

| 打开、新建会话前 | `host/sessions` 的 `exclusive` 里先叫醒；电脑超过 60 秒没人操作时记一行日志、等 1 秒。锁屏时照旧直接回 `locked`，不注入 |

| 有人开始看画面时 | `rc:active` 从 0 变成有人时叫醒一次，再开防息屏 |

### 2.26 "已打开"列表按平铺位置排（被控端 0.9.8，2026-11-20，用户电脑）

用户在手机上说："优化一下，已打开页面窗口的排列显示，不需要最近操作的放在最前"。问了怎么排，选的是"和电脑平铺位置一致"：屏 1 到屏 2、从左到右；电脑上重排后列表跟着变；点进某个窗口操作、刷新列表都不该改变它的位置。

**原因**：`rc:list` 直接用 `win32.enumTargetWindows` 的结果，而 `EnumWindows` 是按窗口的前后顺序给的，最近激活过的在最前。在手机上点进哪个窗口，被控端就把它切到前台，回到列表它就成了第一个，别的都往后挪。App 和网页控制端都照收到的顺序显示，自己不排。

**改法**（只改被控端；消息格式没变，服务器、App、网页控制端都不用改）：

| 部分 | 改了什么 |
|---|---|
| `host/winorder.js`（新） | `sortByPosition(windows, monitors)`：按屏、从左到右、从上到下、句柄排。纯计算，页面不用，只有主进程和测试用 |
| `host/win32.js` | `enumTargetWindows` 每一项多一个 `rect`（屏幕上的位置）；最小化的窗口实际坐标是 (-32000, -32000)，改用 `GetWindowPlacement` 取它还原后会回到的位置。枚举结果本身的顺序没动（`host/sessions` 还按原样用） |
| `host/tiler/index.js` | 新增 `orderedMonitors()`：按平铺配置 `monitor_order` 排好的显示器。自己读配置，不依赖平铺引擎在不在跑 |
| `host/main.js` | `rc:list` 先排再回。`rect` 只在被控端里用，不发给控制端 |
| `host/package.json` | 打包清单加上 `winorder.js`（漏了的话装好的被控端一启动就报找不到模块） |
| 文档 | 03 的 2.4"列表的顺序"，04 的"会话列表页"和 A40 |

**定下来的规则**（完整写在 03 的 2.4）：

- 只看窗口现在的位置，不用平铺引擎上一次的排列计划。平铺摆好的时候两者结果一样；自动平铺暂停了、平铺没在运行（旧的 Python 版在跑、开发时设了 `RC_HOST_NO_TILER`）、用户把窗口拖走了，计划就过时了，位置永远是准的。
- 没参与平铺的窗口（Claude 主窗口、标题被排除的窗口）不单独处理，也按位置排：它摆在哪两个窗口之间，就排在哪两个之间。
- 屏的先后跟平铺配置的 `monitor_order` 走（默认屏幕序号 1、2、3），不是物理上的左右。
- 最小化的窗口按还原后的位置排，最小化、还原都不让它换位置。
- 所有屏都放满以后叠在同一格的窗口，位置一样，按句柄从小到大。句柄和谁在上面无关，所以还是稳定的。

**自动化测试**：被控端 135 个，新增 12 个（`winorder.test.js`：按屏再从左到右；把每个窗口依次提到最前，结果都不变；换了格子列表跟着换；`monitor_order` 的几种写法；主窗口按位置插在中间；同一列从上到下；叠在一格按句柄；最小化的用还原位置；取不到位置的排最后；中心点在屏外算最近的屏；没有显示器信息时只按左右排；不改动传入的数组）。

**原因**（三条都查实了）：

1. 那个会话的 Claude Code 进程是 08:14:36（UTC）启动的，插件 1.0.9 是 09:15:24 装的。钩子在进程启动时加载，所以这个会话用的还是 1.0.8，根本没有卡住提醒的钩子。`hooks.log` 里从头到尾没有一条 `stalled.js` 的记录。2.29 里写的"新开的会话才生效"，对一直开着的会话就是"不生效"。同一个会话在这之前还有一次浏览器调用从 08:53:52 等到 10:55:52，两个小时，同样没人知道。
2. 就算钩子加载了，"调用超过 12 秒"这个判断也不准。把本机所有会话记录里的自带浏览器调用翻了一遍：672 次里，扣掉明确写了等待的时间后仍然超过 12 秒的有一百多次，大多是一批操作里连着打开几个网页，正常就要 17～78 秒，都会误报。
3. 后台钩子在真实会话里从没验证过（2.29 的"没测"第一条）。

**怎么查到更好的办法**：先找到 Claude Code 给每个运行中的会话进程记的登记文件（`%USERPROFILE%\.claude\sessions\<进程号>.json`，有桌面端会话编号、标题、启动时间），再翻 Claude 桌面端的日志，在 `%LOCALAPPDATA%\Claude\logs\main.log` 里找到了准确的记号：每弹一个确认框一行 `Emitted tool permission request <编号> for browser:javascript_tool in session local_…`，点了是 `Received permission response for <编号>: once`，撤回是 `Permission request <编号> for … aborted`，浏览器的框前面还有一段写着网址。截图里那个框对应的就是 02:56:23（本机时间）的那一行。用一个不在 Claude 里的进程（经 WMI 启动的 cmd）确认过，这份日志和登记文件在 Claude 之外也是这个路径、读得到。

2026-11-21 10:10:51 [warn] [CCD] Session local_6cd0adc1-…: denied 1 permission prompt(s) unanswered for 2922s on a scheduled-task run (process untouched)
2026-11-21 10:10:51 [info] [CCDScheduledTasks] A run failed; not retried

1. 认这一行（`[CCD] Session local_…: denied N permission prompt`）：这个会话还在等的框都算结束，已经发出去的提醒收回，`host.log` 记一行"等了 N 分钟没人答，Claude 自己按拒绝处理了"。

### 2.40 "无法把该窗口切到前台"说出是谁挡着（被控端 0.9.30，2026-11-24，本机）

**起因**。用户说很多被控端没有显示器、或者显示器关着电源，手机上"一直提示电脑上无法把该窗口切换到前台"，问是什么原因。这个提示是 `ensureFront` 里三种切前台的办法（`win32.bringToFront`）都没成、电脑又没锁屏时报的（协议第 5 节 `front-failed`），以前不写日志、也不带原因，从现场分不出是哪种。

**最可能的原因**（推断，出问题的电脑没看到）：最前面是以管理员权限运行的窗口。被控端是普通权限，Windows 不让它把这种窗口换下去，也不让它往里发键盘鼠标，三种办法都会失败，而且会一直失败。没显示器的电脑都是远程维护的，任务管理器、管理员终端、安装程序、远程控制软件的窗口留在最前面很常见。另一种可能是远程桌面连着但窗口最小化了。用户选了"先让提示直接说出挡在最前面的是哪个程序"。

| 文件 | 改动 |
|---|---|
| `host/win32.js` | 新增 `processElevation(pid)`（读进程令牌的 TokenElevation：`elevated` / `normal`；令牌读不了是 `denied`，权限比被控端高；进程打不开是 `unknown`）和 `foregroundInfo()`（前台窗口的程序名、标题、权限，没有前台窗口时为 null）。`bringToFront` 判断成没成改用 `isFront`：目标窗口弹出的附属窗口在前台也算，和 `ensureFront` 开头的判断一致，以前这种情况会误报失败 |
| `host/frontblock.js`（新） | 措辞和去重：给控制端的补充说明（"最前面是管理员权限的「任务管理器」（taskmgr.exe），被控端切不走它，请在电脑上关掉或最小化它"；被控端自己是管理员权限时不说"切不走它"），日志里的一行（同一个程序、同样的权限 10 秒内只记一次，标题不算：终端、浏览器的标题会跟着内容变），说明只用 3 秒内的那次失败；标题按字符截，不切开表情 |
| `host/main.js` | `ensureFront` 切不过去、电脑又没锁屏时记下前台信息（粘贴图片、文件走的也是这里，都会记日志；锁屏时切不过去是锁屏的缘故，不记）；`reportError` 报 `front-failed` 时带上 `detail`；启动时看一次被控端自己是不是管理员权限 |
| `host/preload.js`、`host/renderer.js` | `rc:input-error` 多带一个 `detail`，有的话放进 `{ t: "err" }` |
| 安卓 `Protocol.kt`、`PeerSession.kt`、`RemoteController.kt` | `parseInputError` 返回 `InputError(code, detail)`，提示后面接上说明 |
| 鸿蒙 `Protocol.ts`、`PeerSession.ets`、`RemoteController.ets` | `err` 消息多一个 `detail`，`withDetail` 接到提示后面 |
| `web/app.js` | 同上 |
| [03](03-protocol.md) 第 5 节 | 写明 `detail` |

图片、文件的回执（4.5、4.8）没有带说明，切不到前台时手机上还是原来的提示，原因在 `host.log` 里。

- **起因**：用户原来用飞书插件在手机上审批 Claude Code 的工具调用、回答 Claude 的提问。用户要求把这个功能做进 App，范围是工具审批和 Claude 提问，提醒也都在 App 里做，"APP 要完全替代飞书"。
- **做法**：见 [09](09-approvals.md)。新写一个 Claude Code 插件 `claude-plugin/remoteclaude`（不依赖飞书插件），它的 PermissionRequest 钩子把审批写进 `%LOCALAPPDATA%\RemoteClaude\approvals`，被控端盯着这个目录推给手机（协议 2.7），手机的答案写回去，先到的答案生效；电脑上先答了，钩子从会话记录里看出来就撤掉。App 加了审批面板、后台常驻服务和系统通知（见 [04](04-android-client.md)"审批和提问"）。被控端没在运行时插件什么都不做，Claude Code 照常弹自己的对话框。
- **状态**：本机端到端见 2.11。2026-11-19 已上线一部分：服务器白名单（只改了 `hub.js`），用 `release.js` 发布了 0.8.0（电脑被控端没人看画面时自动升级，手机 App 内提示更新）。用户选了"手机装好 0.8.0 再切"。同日切换完成：手机升到 0.8.1，电脑被控端用安装程序升到 0.8.0（自动升级每 4 小时才查一次，没等），装上插件（user 范围），停用飞书插件（飞书的后台监听进程还在跑，没动）。随后在新开的会话里实地测试，结果见 2.13。两个插件同时开着时 Claude Code 怎么合并两个钩子的决定没有文档，可能一边答了另一边还卡着，所以不同时开。
- **验收**：[04](04-android-client.md) 的 A28 到 A31；在真实会话里走一次审批、一次提问、一次"拒绝并说明"。

### T16 发送文件（P1）

- **起因**：手机只能发图片。用户要求任意文件都能发：文件先传到电脑上存下来，被控端把它在电脑上的完整路径复制到剪贴板、粘贴到 Claude 的输入框，Claude 按路径去读。
- **做法**：协议见 [03](03-protocol.md) 4.8，App 端见 [04](04-android-client.md)"发文件"。文件走控制端新建的 `file` 数据通道（不和输入抢一条通道，也不经服务器），16 KB 一块，上限 50 MB（用户定的，经中继走流量），App 一边发一边算 SHA-256，被控端边收边写临时文件、收齐核对后改成正式文件名（同名加"(1)"），存在"下载\RemoteClaude"（配置 `fileDir` 可改），再把路径粘贴进收完时正在查看的窗口。粘贴失败时文件照样留着，路径放进手机输入框。被控端的收文件逻辑在 `host/files.js`（15 个单元测试），App 端在 `files/`。服务器不用改。
- **状态**：三端代码完成（服务器不用改、网页暂不支持），本机端到端见 2.18。2026-11-19 用 `release.js` 发布了 App 和被控端 0.9.0（App 里带上了 2.17 的提示音），电脑上的被控端用安装程序静默装成 0.9.0（经 WMI 启动，约 10 秒重新上线）。剩下：手机升到 0.9.0，在真机上经广州中继发一次文件，在真实 Claude 会话里让 Claude 按路径读一次。顺带修了"开着后台接收审批时回到前台不重连画面"（2.18 末尾）。
- **验收**：[04](04-android-client.md) 的 A33 到 A35；在真实 Claude 会话里发一个 PDF，路径粘贴进输入框，Claude 能读到内容。
- **后续**：断点续传（协议文档第 7 节）；网页控制端发文件；电脑上收到的文件不会自动清理，多了要手动删。

### T17 从手机关闭会话窗口（P1）

- **起因**：用户要求"已打开"页签的每张卡片右上角加关闭按钮，点了就能关掉电脑上对应的 Claude 会话窗口。
- **做法**：协议见 [03](03-protocol.md) 2.8，App 端见 [04](04-android-client.md)"关闭会话窗口"，被控端见 [07](07-claude-sessions.md) 第 4 节。被控端给窗口发 `WM_CLOSE`（和点 × 一样），等它消失再回执、推新的窗口列表，通知别的正在看的手机；主窗口不能关；带标题核对，Claude 复用了句柄时不关错。关闭不删会话、不打断正在跑的任务，所以不确认（用户定的）。服务器白名单多了两种消息。
- **状态**：三端代码、单元测试、本机端到端完成（2.19）。2026-11-19 已上线：生产服务器换上新代码（只改了 `hub.js` 的白名单，旧代码备份 `/opt/remote-claude/src.bak-20261119-close`，换完 `/healthz` 和主站都是 200，电脑和手机 3 秒内重连），用 `release.js` 发布了 App 和被控端 0.9.1，电脑上的被控端用安装程序静默装成 0.9.1（经 WMI 起 `/S --force-run`，约 10 秒重新上线）。剩下：手机升到 0.9.1，在真机上关一次会话窗口。
- **验收**：[04](04-android-client.md) 的 A36；真机上关掉一个会话窗口，电脑上窗口消失，"全部会话"里它还在、能再打开。
- **网页控制端**：没有这个按钮。

### T18 不点开窗口就操作电脑（P1）

- **起因**：用户在手机上说画面页右上角菜单里的功能（重排窗口、所有会话提到最前、暂停自动平铺、锁定电脑、设置）"应该在外面就有，而不应该连上某个窗口才出现"，随后要求解锁也加上；同时要求"全部会话"里环境名换个颜色、点环境能折叠。
- **做法**：协议见 [03](03-protocol.md) 2.9，App 端见 [04](04-android-client.md)"右上角菜单"和"全部会话页签"，解锁密码怎么走见 [06](06-unlock-service.md)。状态和命令改走信令通道，被控端把锁屏、平铺状态推给账号下所有连着的控制端；没连画面时解锁，密码用被控端每次启动生成的公钥加密，密文只认一次。连着画面时照旧走数据通道，旧版被控端、旧版 App、网页控制端都不受影响。
- **状态**：三端代码、单元测试、本机模拟器实测和用户电脑上的平铺实测完成（2.24）。2026-11-20 已上线：服务器白名单（旧代码备份 `/opt/remote-claude/src.bak-20261120-hostcmd`）、被控端 0.9.6（已装到用户电脑，第一次打的包是坏的、电脑离线约 4 分半钟，见 2.24）、App 0.9.4（已发布到服务器，等用户在手机上更新）。剩下：手机升到 0.9.4 后在真机上试；真锁屏后从列表页解锁。上线顺序不要紧（哪一端旧了都只是列表页这几项用不了、提示升级）。
- **验收**：[04](04-android-client.md) 的 A37、A38；真机上锁屏后在列表页输入 Windows 密码解开。
- **网页控制端**：没做，它还是只能在连着画面时用数据通道上的那几条。

### T19 电脑剪贴板的文字同步到手机（P1）

- **起因**：用户在画面里点了 Claude 的"复制"，文字只进了电脑的剪贴板，手机上拿不到。
- **做法**：协议见 [03](03-protocol.md) 4.9，App 端见 [04](04-android-client.md)"同步电脑剪贴板"。被控端在有人看画面时盯着剪贴板序号，文字变了就经 `input` 数据通道分块发给控制端，App 拼齐后写进手机剪贴板并提示。只自动同步、只同步文字（用户定的）。服务器不用改。
- **状态**：被控端和 App 的代码、单元测试完成，用户电脑上实测了被控端这一半（2.27）。2026-11-20 已发布：被控端 0.9.9 已装到用户电脑并传到发布目录，App 0.9.6 已发布到服务器（2.27 末尾）。两边都升级了才能用（哪一边旧了都只是没有这个功能，别的不受影响）。剩下：手机升到 0.9.6 后在真机上试。
- **验收**：[04](04-android-client.md) 的 A41、A42；真机上点 Claude 回复下面的"复制"，切到微信之类的 App 里粘贴出来一致。
- **后续**：剪贴板里的图片；控制端主动取电脑剪贴板里现有的内容；网页控制端；手机到电脑方向的自动同步。

### T20 桌面端自己弹的确认框提醒手机（P1）

- **起因**：Claude 桌面端自带浏览器的"允许 Claude 操作这个网站？"不经过工具审批，手机上没有通知，会话就一直卡在那儿（2.29）。
- **做法**：[09](09-approvals.md) 第 4 节：被控端读 Claude 桌面端的日志，看到弹了确认框就提醒手机（`host/dialogwatch.js`，被控端 0.9.12）。第一版是插件 1.0.9 的 `stalled.js`（按"调用超过 12 秒"猜），对更新前就开着的会话不生效、误报也多，半天后换掉（2.30）。用户先选了只做通知，提醒能用以后选了"加上在手机上直接点"：被控端 0.9.13 起浏览器的框可以在提醒里选"允许一次""拒绝"，被控端替用户按电脑上的按钮（2.31）。
- **状态**：见 2.30、2.31。和会话什么时候开的、加载的是哪一版插件都没有关系，被控端装上就对所有会话生效。
- **验收**：让 Claude 用自带浏览器操作一个没授权过的网站：几秒后手机收到"电脑上有确认框在等你"的提醒，写着会话名和框里问的那句话；在提醒里选"允许一次"，电脑上的框消失、Claude 接着干；或者点开这个会话的画面自己点，提醒自己消失。`host.log` 里有 `[确认框] 提醒手机：…`，以及 `[确认框] …按好了` 或 `[确认框] 收回…`。
- **风险**：靠的是桌面端日志的写法，Claude 升级后可能变。被控端会自己验证（插件的审批连着 5 条在日志里对不上就提醒手机"确认框提醒可能失效了"），收到这条提醒就照 09 第 4 节对一下日志的写法、改 `dialogwatch.js` 里的那几个正则。
- **后续**：在手机的提醒里显示 Claude 要发送的具体内容（现在只有网站和操作的种类）。

### T21 Claude 升级后自检和自动修复（P1）

- **起因**：Claude 桌面端自己升级后界面变了，手机上的新建会话失效，用户用到才发现（2.28）。用户要求每次升级后自动检查、自动修，并选了全自动。
- **做法**：[07](07-claude-sessions.md) 第 8 节。被控端自检加提醒（0.9.11），定时任务 `remoteclaude-claude-upgrade-fix` 自动修复和发版。
- **状态**：被控端 0.9.11 和定时任务都已就位（2.29）。真的"升级后失效 → 自动修好"还没发生过，只验证了各个环节。
- **验收**：下次 Claude 升级后 `host.log` 里有 `[自检]` 的几行、`selfcheck.json` 更新；要是没通过，手机收到提醒，之后定时任务修好并通知。
- **风险**：定时任务会在没人看着的时候打包、安装被控端。提示词里有护栏（只改 `host/sessions`、测试和命令行自检都过才发、装之前核对包和试运行、起不来装回上一版、不推送），但装坏了电脑会掉线，要回到电脑前处理。不想要全自动时，在 Claude 桌面端的"定时任务"里停掉这个任务即可，自检和提醒不受影响。

- ~~每次打开画面带宽估计起步太低~~：0.8.3 起在 answer 里给起步码率（2.14）。

## 4. 开发约定

- **协议是三方约定**。改动消息格式前先更新 [03](03-protocol.md)，并确认被控端、服务器、网页端、安卓端都跟上。
- **安全校验留在被控端主进程**。白名单、前台校验、命中测试不能挪到渲染进程或控制端。
- **密钥和账号数据不入库**。`server/config.json`、`host/config.json`、`deploy/prod/`、`server/data/` 已在 `.gitignore` 里。
- **输入类改动用测试窗口验证**，不要拿用户正在用的 Claude 会话试。
- **先读 [02](02-architecture.md) 的"开发中踩过的坑"**。
